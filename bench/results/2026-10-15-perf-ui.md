# Thread switch with a full reading cache, 2026-10-15

Command, run three times on each side, alternating, on the Linux container
(Ryzen 7 5825U, headless Chrome on ANGLE AMD):

```sh
nice -n 10 bun bench/thread-switch.ts --delay 300 --runs 7 --cached 16 [--ui <origin/main checkout>/packages/ui]
```

The baseline is `origin/main` (2adac07b) with only the fake client's
`&copies=<n>` seed added, so both sides read the same 17 threads of 400
messages to the top before the warm loop. `leaveMs` is the synchronous part of
a click: the task that leaves one thread and paints the next. The heap is
`Runtime.getHeapUsage` after `HeapProfiler.collectGarbage`, two seconds after
the last switch.

| median of 3 runs (each the median of 7 switches) | before | after |
| --- | --- | --- |
| leave the 400-message thread for a short one | 27.9 ms | 10.1 ms |
| leave the short thread for the 400-message one | 22.2 ms | 1.7 ms |
| click to painted messages, cached return | 64.5 ms | 43.9 ms |
| JS heap after the visits | 25.7 MiB | 15.0 MiB |

Per run, before: leave 30.3, 27.9, 26.9 ms and 22.2, 24.6, 21.4 ms; heap
25.7 MiB each. After: leave 10.6, 8.6, 10.1 ms and 1.7, 1.4, 1.8 ms; heap 14.9,
15.0, 15.0 MiB. No page errors on either side.

The leave no longer measures every cached visit again through their proxies
(`ReadingCache` keeps each size beside its entry), and the idle pass after a
leave keeps the visit as plain data instead of the deep `$state` proxy the
timeline drew. The fake's messages are one short text part each; real threads
with tool parts weigh more per message in proxies, so the heap gap grows with
them.

Unmeasured: the display image bound (a hard bound, the common WebP copy is
unchanged), field patching of the open thread on load ticks and the
credential-less liveness probe, where the work removed is plain from the code.

# Phone chat behind the thread list, 2026-10-15

Command, run three times on each side, alternating, against bundles built once
from `origin/main` (2adac07b) and from this branch:

```sh
nice -n 10 bun bench/ui-frames.ts --bundle <dir> --trace --runs 1 --only "phone streaming behind list,phone streaming"
```

"phone streaming behind list" opens the fake's recent thread at 390x844,
starts a streamed answer, taps Back to the thread list and measures 3 s while
the answer keeps streaming behind it.

| median of 3 runs | before | after |
| --- | --- | --- |
| behind list: main-thread CPU per 3 s window | 1,206 ms | 863 ms |
| behind list: paints | 163 | 0 |
| behind list: layouts forced by script | 54 | 2 |
| phone streaming, chat on screen: main-thread CPU | 1,343 ms | 1,293 ms |

Per run, behind list, before: 1,206, 1,191, 1,403 ms; after: 863, 927,
674 ms. The chat on screen does not change (noise). Frame rate stays at 55 to
60 fps on both sides.

# Pull request lookups of sidebar cards

`ThreadCard.test.ts` "cards on screen share one round a minute, none while the
page is hidden, and one on return" counts `threads.pullRequest` calls for ten
idle cards over 120 s with fake timers: 80 before, 20 after. A thread at work
keeps a 15 s round, so a pull request opened during a turn still shows within
15 s. Unmeasured: the Done fold reads and the per-project list sorting, where
the removed work is plain from the code.
