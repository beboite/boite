# File checkpoints: shared blobs, root cache and parent checks

Date: 2026-10-15. Machine: LXC `boite` (Ryzen 7 5825U, 8 CPUs capped, nice 10),
Linux, ext4-backed data directory under `/tmp`. Other jobs ran on the machine
at the same time, so single samples vary by up to 50 %.

Command, run three times on `origin/main` (bd566df4, with this branch's bench
file copied in) and three times on the branch, alternating:

```sh
nice -n 10 bun run bench/checkpoint-files.ts
```

The bench snapshots a flat fixture (1000 identical 32 KiB files) and a nested
one (1000 distinct 4 KiB files three folders deep) directly, then drives two
threads on the nested folder through the core's checkpoints, two turns each,
and a third owner of thread 1 as after a restart. Each value is the median of
the three runs; a "warm" value first takes the median of the warm samples of
each run.

| Case | origin/main | branch |
| --- | ---: | ---: |
| Nested snapshot, warm cache | 343 ms | 169 ms |
| Flat snapshot, warm cache | 58 ms | 56 ms |
| Thread 1, first turn in a new folder | 714 ms | 875 ms |
| Thread 1, later turn | 253 ms | 200 ms |
| Thread 2, first turn in the same folder | 608 ms | 276 ms |
| Restart, first turn of thread 1 | 588 ms | 598 ms |
| Blob files on disk after both threads | 2000 (8.19 MB) | 1000 (4.10 MB) |

- Parent checks once per folder per snapshot: the nested warm snapshot takes
  about half the time; the flat one has no parents to check and stays the same.
- Cache per folder: a second thread's first turn reuses the first thread's
  metadata and only links the blobs.
- Shared store: each content is stored once. The first snapshot of a folder
  no thread has saved before now also creates the shared name of each new
  blob (one hard link and one `lstat` per file), about 160 ms more for 1000
  new files. Every later thread in that folder skips that cost and the read.
- After a restart, a cold snapshot of an existing thread still reads back
  every existing blob, as before the PR: it compares the bytes instead of
  hashing them, so a blob zeroed by a crash is rewritten, then adds two
  `lstat` calls and a link attempt. Not re-measured after the byte compare
  came back.

# Merged-PR archive: processes per pass

Date: 2026-10-15, same machine. The test "unmerged worktree threads cost one git
and one gh call per pass, then wait longer before each new proof"
(`packages/core/test/merged-pr-archive.test.ts`) drives the archive sweep over
four idle worktree threads of one repository, each with an open PR, with fake
`gh` answers and the real `git`. It counts every process the core spawns per
pass. The same scenario, without its assertions, ran three times against the
`origin/main` sources of `pull-requests.ts`, `merged-pr-archive.ts` and
`linked-pull-requests.ts`, then three times on the branch:

```sh
nice -n 10 bun test packages/core/test/merged-pr-archive.test.ts -t "one git and one gh"
```

The counts are the same in all three runs of each side.

| Pass | origin/main | branch |
| --- | --- | --- |
| 1, first proof of 4 threads | 12 (4 status, 4 remote, 4 gh) | 2 (1 remote, 1 gh) |
| 2 and 3, within the minute | 8 each (4 status, 4 remote), 4 proofs | 0, no proof |
| 4, one thread updated | 8, 4 proofs | 0, 1 proof from the caches |
| 5, 5 minutes later | 12, 4 proofs | 2, 4 proofs |
| 6, 10 minutes later | 12, 4 proofs | 0, no proof (next wait 10 minutes) |
| 7, 15 minutes later | 12, 4 proofs | 2, 4 proofs |

On `origin/main` every pass proves every eligible thread again: one `git
status` walk and one `git remote -v` per thread, and one GitHub call per thread
once the 60 second proof cache expires. On the branch a pass reads the
repository's remotes and PR list once, shared with the sidebar badges; `git
status` runs only for a thread whose PR is merged.

## Worktree list, diff and new worktrees

Date: 2026-10-15, same machine. A throwaway script started a test core with a
fresh `BOITE_DATA_DIR`, built a 500-file repository with 50 linked worktrees
and 300 threads in another project, then timed `worktrees.list` 7 times after
one warm call and `git.diff` of one modified file 30 times after one warm
call. It ran against an extract of `bd566df4` (this branch's base) and the
branch, alternating, three times each:

```sh
nice -n 10 bun bench.ts <tree>          # git.diff without oldPath
nice -n 10 bun bench.ts <tree> origin   # git.diff with oldPath: null (branch only)
```

| Median of 3 runs | bd566df4 | branch |
| --- | --- | --- |
| `worktrees.list`, 50 worktrees | 606 ms | 279 ms |
| `git.diff`, no `oldPath` | 24.2 ms | 17.6 ms |
| `git.diff`, `oldPath` given | (not in the contract) | 5.9 ms |

Git processes per `git.diff`, counted by spying on `procs` in
`packages/core/test/git.test.ts` ("one git reads a diff when the client gives
the origin..."): 4 before (`status`, `rev-parse`, `cat-file -s`,
`cat-file blob`), 2 without `oldPath` (`status`, `cat-file --batch -z`), 1 with
it.

`git worktree add` of this repository (1315 files, 16 CPUs) into a local
shared clone, three runs each, alternating:

```sh
nice -n 10 git -c checkout.workers=1 worktree add -q --detach ../w HEAD
nice -n 10 git -c checkout.workers=0 worktree add -q --detach ../w HEAD
```

`checkout.workers=1` (git's default): 314, 332, 336 ms, median 332 ms.
`checkout.workers=0`: 130, 139, 141 ms, median 139 ms.

The eight read slots per core are a bound, not a speedup: unmeasured.
