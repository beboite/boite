# The UI with sixteen agents at work, 2026-10-17

Command, on NUNO-X870 (Ryzen 7 9800X3D, RTX 5080, Windows 11), headless
Chrome compositing on ANGLE Direct3D 11, with other agents running on the
machine:

```sh
bun bench/ui-at-rest.ts --bundle <dir> --runs 2 [--only "<scenario>"]
```

Three bundles of the fake-client UI, built by `bench/ui-frames.ts --build`:

- base: `7c7327ab` with this change's fake client (`?working=16`, the trace
  method), nothing else;
- at rest: the loops paused by `var(--loops)`, still eased smoothly;
- final: the working-state loops also on the 60 Hz grid.

Each line is one 6 s window: CPU milliseconds per wall second of Chrome's
renderer and GPU processes, the browser process, the renderer's main thread
(`ThreadTime`), and the frames the compositor drew (`DrawFrame`).

## Reading

- In front, renderer and GPU went from 550 to 572 ms/s to 211 to 218: 62 %
  less. The frames fell from 352 to 63 a second, the 60 Hz grid.
- Behind another application, from 500 to 513 ms/s to 20 to 47: 93 % less.
  The 2.8 frames left are the clocks and progress lines that change once a
  second.
- Streaming is unchanged: the fake agent writes a token every 16 ms, about
  2,000 characters a second, ten times a real stream, and the main thread's
  layout of it sets a frame on every refresh. A blurred window behind a
  streaming answer still draws it.
- The GPU process of the phone list reads 88 to 90 or 374 ms/s on the same
  base bundle; its figures are the noisiest here.

## Process events

`process.started` and `process.exited` arrive about 180 a second under
sixteen agents. The old handler put each one in a list that only grew, copied
twice per process. Plain arrays in Bun, the same work as the handler
(`D:/Dev/.temp` script, not kept), 90 starts and exits a second:

| Rows held | Old, per start and exit | Old, per second | Bounded to 200, per second |
| --- | --- | --- | --- |
| 5,400 (1 min) | 0.105 ms | 9 ms | 0.9 ms |
| 54,000 (10 min) | 0.647 ms | 58 ms | 0.7 ms |
| 324,000 (1 h) | 11.4 ms | 1,029 ms | 0.4 ms |

The events are now dropped until the trace surface is on screen, which reads
`trace.get` when it shows, and the list keeps `TRACE_LIMIT` rows.
